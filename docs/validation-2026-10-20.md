# 2026-10-20 部署与验证记录

版本：0.1.0。环境：一台使用 firewall4/nftables 的 iStoreOS 路由器，以及同一 LAN 内一台 Windows 电脑上的 ego-lite 浏览器。测试时间为北京时间。本文仅保留汇总结果。

## 最初故障

机械设计课程在切换分集、跳转到未缓冲位置时出现间歇停滞，部分等待超过 10 秒仍未恢复。对同一视频节点、同一段 202,128 字节内容进行直连对照：

| 连接 | 耗时 | 结果 |
|---|---:|---|
| 首次 IPv6 | 12.002 秒 | 仅收到 73,221 字节，超时 |
| 首次 IPv4 | 0.091 秒 | 完整返回 |
| IPv6 重试 | 0.087 秒 | 完整返回 |
| IPv4 重试 | 0.086 秒 | 完整返回 |

抓包可见重传，但没有定位到具体故障链路或运营商节点。IPv6 存在间歇恢复，不能由单次结果认定所有 IPv6 连接均有问题。

## 播放与跳转对照

| 阶段 | 通过样本 | 未缓冲位置跳转 | 跳转恢复耗时 | 视频请求数 | 视频响应地址族 |
|---|---:|---:|---|---:|---|
| 临时规则前的短期基线 | 6/6 | 3 次 | 0.153–0.461 秒 | 128 | IPv4、IPv6 |
| 单电脑临时 IPv4 回退 | 6/6 | 3 次 | 0.369–0.773 秒 | 142 | 全部 IPv4 |
| 正式服务 | 13/13 | 8 次 | 0.334–0.627 秒 | 293 | 全部 IPv4 |

正式服务覆盖机械设计、工程热力学、计算方法三门课程，共五个分集；跳转恢复耗时中位数为 0.482 秒。浏览器代理关闭后刷新复测，视频响应使用公网 IPv4，普通站点 API 仍能使用 IPv6。

机械设计另一轮连续播放观察 59.95 秒，播放进度推进 59.89 秒，结束时缓冲约 70.1 秒；56 个视频请求均使用 IPv4，开始播放后无等待事件、无丢帧。

代理开启期间的样本、规则未正确加载的样本以及缺少页面探测数据的样本均未纳入以上结果。临时规则前 IPv6 已短暂恢复，短期基线也通过，因此这些数据证明回退生效、当前播放正常，不能证明相对正常 IPv6 存在速度提升，也不能证明长期卡顿已根治。

## 服务与回退验收

- 实际路由器 Lua 通过 24 组合成报文，覆盖域名边界、三个视频域名后缀、HTTP 8082、TLS 4483、错误端口与 IPv4 排除、TCP 分段与缺口、VLAN、pcap 链路格式和大小端、畸形 TLS。
- Shell 语法检查通过；启动、停止、恢复规则、完整卸载、重新安装、同版本重复安装均通过。
- 卸载后配置恢复至变更前状态；安装文件与交付版本一致；已验证目标 IPv6 规则命中。
- 网络、firewall、DHCP、Open-Box 和原有小红书服务的受保护配置保持一致；IPTV 接口保持运行、接口错误计数为零。
- 正式服务设置为开机启动，测试结束后保持运行；临时试验规则和部署临时文件已移除。

仓库中的 `tests/test_learner.py` 包含 14 个测试方法，使用合成报文且不会修改路由规则。GitHub Actions 在 Ubuntu/Lua 5.1 中运行这些测试及 Shell 语法检查；CI 结果不能替代路由器和浏览器验收。

## 尚未覆盖

没有重启路由器验证启动顺序，没有实机观看 IPTV，没有逐一验证其他终端、全部课程、所有 CDN 和长时间网络波动。共享 CDN 地址、加密 ClientHello、独立 DNS 和新端口仍可能影响识别或兼容性。后续再次卡顿时，应重新核对视频连接地址族和真实等待时间；完整停用方法见[运维说明](operations.md)。
